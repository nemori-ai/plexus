# 更新日志 {#更新日志}

这里记录每个版本给运行 Plexus 的人带来了哪些变化。线上协议契约单独计版本，变化也慢得多，见[协议](/zh/protocol/)。

::: tip
带版本标签的发布及其完整提交历史，都可以在 [GitHub](https://github.com/nemori-ai/plexus/releases) 查看。
:::

## 0.9.1：连接你日常登录的浏览器 {#_0-9-1——够到你真正登录着的那个浏览器}

这一版让 `attach` 能够连接你日常使用的 Chrome，也增加了第三条传输通道。

- 正式支持 `chrome://inspect` 开关。自 Chrome 136 起，Chrome 二进制程序拒绝在默认 profile 上使用 `--remote-debugging-port`。因此，在这一版支持的直接连接方式中，要连接默认 profile 里已经登录的浏览器，唯一的入口就是这个开关。它提供的调试暴露面与传统 flag 不同，两种形态在这一版中接入了同一个连接门面。
- Chrome 扩展成为第三条传输通道，也能用于你的常规 profile。使用扩展，只需在安装时同意一次，不必每次连接都重新同意。扩展承担的是传输工作，allowlist、批准与审计仍然留在网关里执行，页面不能改变这些约束。
- 点击和输入改用真实输入事件。有些自定义表单控件和富文本编辑器会忽略直接写入 DOM 的内容；改用输入事件后，它们就能收到 agent 发来的内容。如果点击目标被其他东西盖住，这次点击会被拒绝。
- 标签页在列出之前就会经过过滤。即使浏览器开着 25 个标签页，agent 也只能看到已授权域名上的那些，其余标签页不会出现在列表里。

## 0.9.0：控制浏览器 {#_0-9-0——browser-control}

这一版增加了一个能操作真实 Chrome 的 source，归为 `execute` 级。它支持导航、读取、点击、输入、截图和上传，通过 DevTools Protocol 与浏览器通信，不依赖 Puppeteer 或 Playwright，也不下载浏览器。

作为所有者，你首先要决定把哪个浏览器交给 agent：一个全新、空白、没有登录身份的 profile，还是你自己已经登录的那个。这个选择决定了操作可能影响的范围。同样是控制 Chrome，交出去的浏览器里有没有你的登录身份，才是影响范围的关键。

站点范围则由你掌握的域名 allowlist 来限定。Chrome 自己的同意授权的是访问那个浏览器，并没有替你选定一组可以访问的站点。因此，Plexus 会针对真实目标 URL 做校验，而且每次动作之前都会重新校验。连上浏览器之后，每一步操作仍然受这份名单约束。

在允许操作的页面内，页面暴露面是开放的：可以执行任意 JavaScript，也可以原样透传页面级 CDP。原因是，agent 在一个本来就能操作的页面里，靠点击和输入已经能行使完整的用户操作能力。

真正需要扣住的是浏览器全局的那部分 CDP。这一版没有开放它，域名 allowlist 才能成为实际的边界。页面内允许做什么，与能不能越过页面去控制整个浏览器，是这里分开的两件事。

上传还有独立的目录限制。你必须先指定一个目录，上传的文件只能来自那里；在你指定目录之前，所有上传都会被拒绝。

见[暴露一个 source](/zh/guide/first-party-sources#browser-control)。

## 0.8.0：长调用不再占着连接，控制台提供更多信息 {#_0-8-0——长调用不再堵着-控制台说得更多}

耗时数分钟的 capability 现在会立即返回一个异步 `invoke` 句柄，不必一直占着连接。agent 等结果就绪后，再凭句柄取回结果。

控制台新增了 Activity 概览条，一眼就能看到最近发生了什么。沙箱运行的失败输出会先经过脱敏，再交给 agent。agent 协议也做了加固：拒绝信息会带上足够的说明，让 agent 能自行纠正请求，不必靠猜。

## 0.7.0：首个公开发布 {#_0-7-0——首个公开发布}

0.7.0 是项目首次公开发布的版本。这时，信任模型已经定型，机器上也有了足够多的真实 source，值得接一个 agent 上来使用。

个人数据可以作为第一方 source 接入。Apple Notes、Mail、Contacts、Photos 和 Shortcuts 在这一版加入了 Calendar 和 Reminders。此外还有浏览器标签页、书签和历史，三者都只提供读取；Obsidian 则支持搜索和追加。

这一版确立了发现范围的边界：agent 只能看见所有者授权给它的那个子集。发现阶段不再广播整份目录，agent 能扫描到的，就是你授予它的那部分。请求一旦超出子集，就会直接被拒绝，不会挂成待审批请求，等你再来批准。能发现一项 capability，也不等于已经获得了调用它的全部许可。

0.7.0 引入的默认授权规则是：带副作用的 capability 逐次批准。连接时勾选一个 `write` 或 `execute`，不再等于给它常驻授权；按这一版的默认设置，之后每次调用都要询问所有者。要让它常驻，所有者必须另行主动选择。这个 opt-in 按 capability 逐项设置，默认关闭，还要经过双重确认。因此，连接时选定哪些能力可见，与是否允许其中某项能力常驻，是分开的决定。

会话采用 fail-closed。撤销意味着彻底停止，不是过一段时间才停止。

这一版提供了四种安装 agent 的形态，其中包括 in-context，供没有文件系统、也没有 shell 的 agent 使用；这样的环境也能接入。配套的快速上手会从头走完整个闭环，让使用者能按步骤完成端到端的使用过程。

编码类 agent 使用各自的原生沙箱，不在外面再套一层。

## 0.7 之前 {#_0-7-之前}

0.6.0-rc.1 是首个公开候选版。这一版重构了桌面和运行时，统一了授权与信任模型。What I expose 视图按 Connector → Source → Capability 的层级组织。首批 Apple source 也在这时加入，每个 source 都有各自的健康状态（health）。

0.4.0 让 capability source 可以直接受管理：在控制台或 CLI 里，就能实时添加、启用、重新配置和移除，不用 flag，也不用重启。重新配置若涉及某个 source 的安全面，它已有的授权就会被清空。

0.3.x 集成了 Claude Code 和 Codex，让主流编码 agent 能用上 Plexus 暴露的能力。Obsidian 也支持了读取和写入，走的是它自己的 Local REST API。

0.2.x 开始建立扩展生态。manifest 规范公开了，用户可以自己编写 skill 和 workflow。macOS 也有了首次运行流程，带你从安装一路走到接上一个 agent。

0.1.x 建起了网关，确定了 M0 协议契约，也定下了后来一切所依赖的授权原则：默认由所有者参与并批准授权，agent 永远不能给自己授予一次 `write` 或 `execute`。
