# 授权可扩展性——门票与工牌 {#授权可扩展性——门票与工牌}

::: tip 本页写给谁
如果你正在判断 Plexus 1.0 能否不经破坏性重写，就扩展到任务级与企业级授权，或日后要动手扩展、需要知道哪些接口是刻意预留的，可以从这里看起。这项决定已锁定为 ADR-020，见[决策记录](https://github.com/nemori-ai/plexus/blob/main/docs/protocol/DECISIONS.md)。仓库内的 SSOT 是 [`authz-extensibility.md`](https://github.com/nemori-ai/plexus/blob/main/docs/design/authz-extensibility.md)。
:::

1.0 交付完整的工牌，门票则只交付原型。完整门票被刻意推迟，但它将来需要的每一个联结键、预留字段和收口点，现在都已存在，本页记录并保证这些约定。

## 授权按什么来算——门票与工牌 {#授权的两种单位——门票与工牌}

用户想的是完成一个任务，网关执行的却是一次次 capability 调用。两者的单位不同。如果让人面对二十张一模一样的审批卡，在调用粒度上反复作任务粒度的决定，批准就容易变成肌肉记忆。这不是说每次调用都必须重新批准，而是说，授权同意需要有按任务组织的方式。

先分清身份和权限。工牌回答“你是谁”：它是持久的、按 agent 独立的 PAT，作为长生命期身份使用，可以单独撤销，本身永远不构成权限，见[安全模型](/zh/architecture/security-model)。

门票回答“你此刻可以做什么”。完整设计中的门票以任务为界：任务开始时批准一次，进行中生效，结束时关闭。它还能把整段工作说清楚，例如“这个 agent 在这份授权下整理了这个 vault”。

批准可以从按次放宽到按任务，审计和撤销却不能跟着变粗。每次进出仍有日志，保留逐次调用的审计轨迹；撤销只需一个动作，立即生效，门票撤销后所有成员一起失效。授权粒度、审计密度和撤销速度之间存在取舍。1.0 固定住后两项，才为第一项的放宽留下空间。

1.0 实际交付的门票原型叫任务 bundle。一个 bundle 是 N 条共享 `bundleId` 标签的普通常驻授权，可以一次批准、一次撤销，并附带上下文；它不构成新的权限类别。

原型缺的是生命周期：没有开票和关票，没有任务边界，也没有门票级的叙述。这些属于 ADR-020 推迟的完整门票对象，预留接口供它日后接入。

1.0 管理控制台暂不提供 bundle 创建界面。端点及其与 grant-service 的耦合作为保留机制交付，bundle 成员在界面上仍显示为普通常驻授权；等门票生命周期落地后，再重新引入这层界面。


## 接缝——1.0 固定下来的约定 {#接缝——1-0-锁定了什么}

### S1——grant 删除后，bundle 联结键仍在 {#s1——bundle-联结键比-grant-行活得久}

撤销会删除 grant 行，而不是留下一个失效标记。这是有意的：行不存在，refresh 就无法再凭这条授权铸出 token，撤销才是终局。但这也意味着，grant 存储不能负责保存“哪个任务之下授权了什么”。这份记录必须交给审计日志。

因此，`bundleId` 要随每条授权生命周期审计事件写入；撤销时，必须在删除行之前捕获它。再铸也不能丢掉任务归属：

| 生命周期阶段 | 事件携带 |
| --- | --- |
| agent 请求一个具名 bundle | `grant.pending` + `bundleId` + `bundleName` |
| 人批准该 pend | `grant.allow` + `bundleId` + `bundleName` |
| 成员在范围内的普通再铸请求 | `grant.allow` + `bundleId`（保留原有联结键，不脱离 bundle） |
| 管理员一步建 bundle | `grant.allow` + `bundleId` + `bundleName` |
| 按对 / 按 agent / 按 bundle 撤销 | `grant.revoke` + `bundleId`（三种方式都在删除前捕获） |

这样，即使授权账本里已查无此行，仍能单凭审计日志重放任务 bundle 从 pend → allow → 再铸 → 撤销的完整过程。但重放有保留期限制：日志是只追加的 JSONL，默认保留 90 天。部署若需要更长的重放窗口，调大保留期即可，其他机制不变。

### S2——Attribution 留出“谁、为何”的字段 {#s2——attribution-预留了企业级的-谁-为何-字段}

任务归属之外，每条审计事件还可以携带 `Attribution`：`agent` 记录谁做的，`principal?` 记录代表谁，`grantRef?` 指向准许这次操作的授权，`policyRef?` 指向作出裁定的策略规则。其中，`principal?` 和 `policyRef?` 留给企业级归因。

这些字段全部可选，单网关的 1.0 部署既不写也不读它们。预留字段不等于已经交付企业级行为；企业归因仍待实现。将来的门票层或策略层可以在这里填入归因信息，不必改变现有审计事件的形状。


### S3——信任窗口按加法扩展 {#s3——信任窗口按加法扩展}

授权何时过期，不需要各处分别判断。`TrustWindowKind` 是闭合联合：`once | 1h | 1d | 7d | until-revoked | custom`，过期解析只在一个地方收口。

这让新增窗口可以按加法处理。例如，将来可以增加 `until-task-closed`，由任务关闭事件决定过期，而不是看时间戳。这还不是已交付的窗口；按预留的扩展方式，只需增加一个协议小版本号，再在一个函数里添一个分支。

兼容性有明确前提：新窗口在被提供之前根本不会出现。因此，已存的授权、线上的客户端和管理 UI 都不会因这次新增而损坏。扩展的是有效期的表达方式，不是权限范围。

### S4——授权器是可插拔的策略接缝 {#s4——授权器是可插拔的策略接缝}

谁来裁定授权，也与线上契约分开。授权决策放在 `Authorizer` 接口之后，这就是 ADR-007 的“换策略不动线上契约”。1.0 内置两个实现：`auto-approve` 用于受信管理员路径，`confirm-risky` 是默认的 pend 策略。

将来的企业级策略引擎可以作为第三个实现接入，对照门票、角色和组织规则作出裁定，再经由 S2 的 `policyRef` 汇报裁定，线上契约无需改动。这是预留方向，不是已交付的引擎。替换策略实现，同样不意味着多出一层权限。

### S5——门票永远不能放大权限 {#s5——门票永远不能放大权限}

无论未来门票对象长成什么样，都要继承 bundle 的结构性规则：分组不赋予超出其成员的任何权限。每个成员仍是一条走过普通审批闸门的普通常驻授权；整组也与任何授权一样，随 connection-key 轮换一起失效。

门票是同意与叙述的对象，永远不是与授权、token、暴露并列的第四种权限类别。暴露仍是独立要求：有效访问始终是已授权 ∧ 已暴露，按 capability 计，在管线里实时强制执行。


## 门票之内的 execute——ADR-023 只回答了一部分 {#门票之内的-execute——已部分回答-adr-023}

“帮我整理这个 vault”可能合理地包含一段 `claudecode.run`。如果任务已经批准，门票内每次 execute 却仍要弹出审批，这张门票就不完整；如果只因调用属于门票，就悄悄免掉审批，又留下了权限漏洞。任务级同意究竟能覆盖到哪里，execute 把这个设计问题摆到了眼前。

早先的表述把 `execute → once` 当作结构性的绝对天花板：execute capability 永远不能获得常驻授权，即使管理员给出信任窗口也不行，见[信任模型](/zh/concepts/trust-model)。这不是当前规则的全部。ADR-023 已将它放宽为默认值加拥有者覆盖：拥有者可以为特定 agent 的特定 execute capability 开启常驻授权。开关默认关闭，连接时需要双重确认。它回答了谁能放宽、怎样放宽，却没有构建门票对象；未来门票仍须遵守三条约束：

1. 只有拥有者能开启常驻 execute。agent 不能自选，也不能靠请求为自己提权；这只能是拥有者经过警示后，刻意作出的按 agent、按 capability 的覆盖。没有这项覆盖时，execute 逐次挂起审批的默认下限不变。
2. 同意必须同时指向某一个 agent 和某一项 capability，由拥有者逐项自愿开启。允许这个 agent 常驻使用这一项 execute，不等于允许其他 agent 或其他 capability，更不因成为门票成员就获得通用 execute 特权。
3. 门票内的 execute 仍受有界窗口约束，不能自动取得超出该窗口的 `until-revoked`；只有拥有者在那次逐项开启中明确选择了 `until-revoked`，才适用这个例外。

因此，当前的界线不是“execute 永远只能用一次”，而是“默认逐次审批，只有拥有者能逐项覆盖”。ADR-023 解决了这一处冲突，完整门票如何构建，留到最后一节继续。


## 未来的门票对象会补上什么（草图，非规范） {#未来的门票对象会补上什么-草图-非规范}

完整门票仍是待做的设计，不属于 1.0。按这份草图，将来可以直接沿着上述接缝构建对象，无需迁移。要补的是三部分。

生命周期从开票开始：批准动作开票，随后处于生效中；用户动作、任务结束或窗口过期，都可以触发关票。“关闭”是要新增的状态，由 S3 以一种窗口类型承载，不是当前已经具备的行为。

边界包括任务的范围约束和上下文。bundle 今天已经把它们编成组，未来的门票对象可以从这层分组接上任务边界。
